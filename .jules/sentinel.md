## 2026-03-29 - [CRITICAL] Fix buffer overflow in UNIX socket path
**Vulnerability:** A heap/stack buffer overflow vulnerability existed in `Rconnection::connect()` in `Rconnection.cpp` where the user-supplied `host` string was copied into the `sau.sun_path` buffer without bounds checking using `strcpy()`. If the `host` string exceeded the size of `sau.sun_path` (typically ~108 bytes on Unix systems), it would result in memory corruption, potentially leading to arbitrary code execution or a denial of service.
**Learning:** Legacy C code often relies on unsafe string manipulation functions like `strcpy()` without prior length validation. Even seemingly innocuous connection parameters like `host` paths can be exploited if they are user-controlled and unvalidated.
**Prevention:** Always use safe string functions (e.g., `strncpy()`, `snprintf()`) or perform explicit bounds checking against the destination buffer's `sizeof()` before copying data, especially when dealing with fixed-size struct fields like those in `sockaddr_un`. **Vulnerability:** A heap buffer overflow existed in `Rconnection::login` where the `authbuf` buffer size was calculated assuming the output of `crypt()` would be roughly the size of the plaintext password. If a modern crypt algorithm (e.g., SHA-512) is used, the returned hash exceeds the buffer allocation, leading to memory corruption. Furthermore, there was no `NULL` check on the `crypt()` return value, risking a denial of service via segmentation fault.
**Learning:** Never assume the length of cryptographic hash outputs when allocating memory. Algorithms and salt formats change over time, and modern algorithms output significantly longer strings than legacy ones like DES. Always check the return values of library functions that can fail, like `crypt()`.
**Prevention:** Always evaluate the size of a dynamically generated string (e.g., via `strlen()`) *after* generation and *before* allocating memory for it. Implement robust `NULL` checks for functions that return pointers.
