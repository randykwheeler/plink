## 2026-03-29 - [CRITICAL] Fix buffer overflow in UNIX socket path
**Vulnerability:** A heap/stack buffer overflow vulnerability existed in `Rconnection::connect()` in `Rconnection.cpp` where the user-supplied `host` string was copied into the `sau.sun_path` buffer without bounds checking using `strcpy()`. If the `host` string exceeded the size of `sau.sun_path` (typically ~108 bytes on Unix systems), it would result in memory corruption, potentially leading to arbitrary code execution or a denial of service.
**Learning:** Legacy C code often relies on unsafe string manipulation functions like `strcpy()` without prior length validation. Even seemingly innocuous connection parameters like `host` paths can be exploited if they are user-controlled and unvalidated.
**Prevention:** Always use safe string functions (e.g., `strncpy()`, `snprintf()`) or perform explicit bounds checking against the destination buffer's `sizeof()` before copying data, especially when dealing with fixed-size struct fields like those in `sockaddr_un`. **Vulnerability:** A heap buffer overflow existed in `Rconnection::login` due to a hardcoded size allocation (`strlen(user) + strlen(pwd) + 22`) for the `authbuf`. When `crypt()` was used (e.g., on Unix systems with modern hash algorithms like SHA-512), the resulting hash length could easily exceed 86 bytes, causing `strcpy` to overflow the heap buffer. Additionally, there was a null pointer dereference risk as `crypt()`'s return value wasn't checked for `NULL` before being passed to `strcpy`.
**Learning:** Legacy hardcoded size limits for cryptographic outputs (often assuming old 13-byte DES hashes) are incredibly dangerous when systems switch to modern, longer hash algorithms. Always dynamically calculate buffer sizes based on the *actual* output length of external functions like `crypt()`.
**Prevention:**
1. Always capture the output of `crypt()` and immediately check for `NULL` before any further processing.
2. Dynamically allocate memory based on `strlen()` of the actual strings that will be copied (e.g., `strlen(user) + strlen(final_pwd) + 2`), avoiding arbitrary constants.
3. Check the return value of `malloc` for `NULL`.
