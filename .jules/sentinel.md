## 2026-03-29 - [CRITICAL] Fix buffer overflow in UNIX socket path
**Vulnerability:** A heap/stack buffer overflow vulnerability existed in `Rconnection::connect()` in `Rconnection.cpp` where the user-supplied `host` string was copied into the `sau.sun_path` buffer without bounds checking using `strcpy()`. If the `host` string exceeded the size of `sau.sun_path` (typically ~108 bytes on Unix systems), it would result in memory corruption, potentially leading to arbitrary code execution or a denial of service.
**Learning:** Legacy C code often relies on unsafe string manipulation functions like `strcpy()` without prior length validation. Even seemingly innocuous connection parameters like `host` paths can be exploited if they are user-controlled and unvalidated.
**Prevention:** Always use safe string functions (e.g., `strncpy()`, `snprintf()`) or perform explicit bounds checking against the destination buffer's `sizeof()` before copying data, especially when dealing with fixed-size struct fields like those in `sockaddr_un`. Ensure that out-of-bounds conditions result in secure failure paths (e.g., returning an error code and cleaning up resources).
## 2026-04-21 - [CRITICAL] Fix heap buffer overflow in Rconnection login
**Vulnerability:** A heap buffer overflow existed in `Rconnection::login()` where memory allocation for an authentication buffer assumed a maximum fixed size for the output of `crypt()` (e.g., `strlen(pwd) + 22`). Modern `crypt()` implementations (like SHA-512) can produce hashes exceeding 100 bytes, leading to a buffer overflow when blindly copied with `strcpy()`. Additionally, missing NULL checks for `malloc()` and `crypt()` could cause segmentation faults.
**Learning:** Never assume the length of cryptographic algorithm outputs, as system defaults evolve. Always dynamically allocate memory based on the exact output length at runtime.
**Prevention:** Call functions that produce variable-length output first, check for errors (e.g., NULL pointers), calculate the exact required buffer size dynamically using `strlen()`, and verify that memory allocation (`malloc()`) succeeds before proceeding with secure copying.
## 2024-05-01 - [CRITICAL] Fix buffer overflow in sisocks.h snprintf polyfill
**Vulnerability:** A critical buffer overflow existed in the custom `snprintf` polyfill for Windows platforms in `sisocks.h`. The polyfill used the unsafe `vsprintf` function, completely ignoring the passed `len` parameter. An attacker could exploit this by triggering socket errors that generate overly long error messages, overwriting the bounds of the provided buffer. Additionally, `sprintf` was used unprotected in `sockerrorchecks` on non-Unix platforms.
**Learning:** Custom polyfills for standard library functions (like `snprintf`) must faithfully implement the safety guarantees of the original function. Falling back to unsafe variants (`vsprintf`) defeats the purpose of the polyfill. On MSVC, `_vsnprintf` does not guarantee null-termination upon truncation, requiring explicit manual null-termination.
**Prevention:** Always use safe bounds-checked formatting functions like `vsnprintf` or `_vsnprintf`. When using `_vsnprintf` on Windows, manually add a null terminator to the end of the buffer (`buf[len-1] = 0;`) to prevent non-null-terminated strings from causing subsequent out-of-bounds reads.
