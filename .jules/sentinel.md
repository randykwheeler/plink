## 2026-03-29 - [CRITICAL] Fix buffer overflow in UNIX socket path
**Vulnerability:** A heap/stack buffer overflow vulnerability existed in `Rconnection::connect()` in `Rconnection.cpp` where the user-supplied `host` string was copied into the `sau.sun_path` buffer without bounds checking using `strcpy()`. If the `host` string exceeded the size of `sau.sun_path` (typically ~108 bytes on Unix systems), it would result in memory corruption, potentially leading to arbitrary code execution or a denial of service.
**Learning:** Legacy C code often relies on unsafe string manipulation functions like `strcpy()` without prior length validation. Even seemingly innocuous connection parameters like `host` paths can be exploited if they are user-controlled and unvalidated.
**Prevention:** Always use safe string functions (e.g., `strncpy()`, `snprintf()`) or perform explicit bounds checking against the destination buffer's `sizeof()` before copying data, especially when dealing with fixed-size struct fields like those in `sockaddr_un`. Ensure that out-of-bounds conditions result in secure failure paths (e.g., returning an error code and cleaning up resources).
## 2024-05-18 - [CRITICAL] Fix heap buffer overflow in authentication logic
**Vulnerability:** A heap buffer overflow existed in `Rconnection::login()` where the allocated buffer for the authentication string was fixed at `strlen(user) + strlen(pwd) + 22`. However, when using `crypt()`, the resulting hashed password length can potentially exceed this arbitrarily chosen extra 22 bytes depending on the platform/crypt algorithm, overflowing the heap buffer. Additionally, there were no checks if `crypt()` or `malloc()` failed and returned `NULL`, which would lead to a segmentation fault when passing it to `strcpy()`.
**Learning:** Hardcoding "buffer padding" (like `+22`) for dynamically generated content like cryptographic hashes is a highly unsafe pattern. The size of the output from system functions like `crypt()` must be verified, and error conditions (like returning `NULL`) must be handled securely.
**Prevention:** Always allocate buffers dynamically based on the actual length of the inputs being concatenated, calculate the length *after* generating the hash, and handle `NULL` returns from allocation and system functions securely by returning error codes instead of crashing.
