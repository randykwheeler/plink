## 2026-03-29 - [CRITICAL] Fix buffer overflow in UNIX socket path
**Vulnerability:** A heap/stack buffer overflow vulnerability existed in `Rconnection::connect()` in `Rconnection.cpp` where the user-supplied `host` string was copied into the `sau.sun_path` buffer without bounds checking using `strcpy()`. If the `host` string exceeded the size of `sau.sun_path` (typically ~108 bytes on Unix systems), it would result in memory corruption, potentially leading to arbitrary code execution or a denial of service.
**Learning:** Legacy C code often relies on unsafe string manipulation functions like `strcpy()` without prior length validation. Even seemingly innocuous connection parameters like `host` paths can be exploited if they are user-controlled and unvalidated.
**Prevention:** Always use safe string functions (e.g., `strncpy()`, `snprintf()`) or perform explicit bounds checking against the destination buffer's `sizeof()` before copying data, especially when dealing with fixed-size struct fields like those in `sockaddr_un`. **Vulnerability:** A heap buffer overflow existed in `Rconnection::login()` because it allocated memory based on the length of the plaintext password plus a fixed offset (`22` bytes), assuming `crypt()` returns a short fixed-length hash (e.g. 13 chars). Modern `crypt()` implementations can return significantly longer strings (e.g. 86+ chars for SHA-512), causing `strcpy()` to write past the allocated buffer bounds.
**Learning:** Never assume the length of the output of cryptographic functions like `crypt()` without verifying it. Fixed-size buffer allocations for potentially variable-sized cryptographic hashes are a major risk for heap overflows.
**Prevention:** Compute the hash first, evaluate its length explicitly, and dynamically allocate the buffer to fit the exact size of the generated hash plus any required formatting characters and the null terminator. Always handle potential `NULL` returns from both the cryptographic function and memory allocator.
